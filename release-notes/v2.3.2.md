# Morrow v2.3.2 — Releases are made by git alone

**Release date:** 2026-11-01
**Toolchain:** `forge 2.3.2 (morrow standalone 2026)`
**Self-hosting fixed point:** `45CABA386388A85973B408AA1718C0F7343BFE093E21DAEEFA027F3B61A89193`
(`target/stage2.exe.ll` == `target/stage3.exe.ll`)

The local pipeline exists to *replace* hosted release tooling. v2.3.1's pipeline
still leaned on one: `gh` for preflight auth and for creating/updating the release
page. That made the "local" path depend on the thing it was supposed to replace —
and it contradicted the point of a self-hosted toolchain. This release removes that
dependency completely.

## Publishing is now `git` and nothing else

| Before | After |
|---|---|
| `stage_publish` called `gh release view / create / edit / upload` | `git commit`, `git tag -a`, `git push`, `git ls-remote` |
| Preflight required `gh auth status` | Preflight requires a git work tree, a checked-out branch, and an `origin` remote |
| Release existed only if a host API call succeeded | Release **is** the annotated tag; the artifacts live in `dist/vX.Y.Z/` |
| `--draft` (host-API concept) | Removed |

A release can now be cut on any machine with `clang` and `git` — offline, against a
mirror, or in a fork whose remote is not GitHub at all. Host CLIs remain a
contributor convenience for working from forks; they are deliberately out of the
release path, and `RELEASE_PROCESS.md` §6 says so explicitly.

## The tag is verified, not assumed

`git push` returning 0 is not proof that the tag exists on the remote. The publish
stage now reads the remote's refs (`git ls-remote --tags origin`) and checks **two**
things: the tag object id matches the local annotated tag, and its peeled commit id
equals `HEAD`. A push absorbed by a proxy, blocked by a pre-receive hook, or landing
on the wrong commit fails the stage instead of being reported as a release.

Two Windows-specific defects were found and fixed while rehearsing this against a
throwaway bare repository:

1. **Truncated paths.** `git status --porcelain` output was `strip()`ed as a whole,
   which ate the leading space of the first entry, so ` M scripts/pipeline.py` was
   parsed as `cripts/pipeline.py`. The dirty-tree guard then named a file that did
   not exist. Entries are now split first and sliced per line.
2. **Silently skipped comparison.** The peeled-ref pattern `refs/tags/vX^{}` was
   passed on a `cmd.exe` command line, where `^` is the escape character; git
   received `refs/tags/vX{}`, matched nothing, and the peeled check quietly passed
   with nothing compared. The refs are now fetched wholesale and filtered in Python.

## The release record travels with the artifacts

`dist/vX.Y.Z/PUBLISH.txt` is written by the publish stage:

```
Morrow v2.3.2

commit:       8aa59ec…
branch:       main
remote:       <origin url>
fixed point:  45CABA38…61A89193
tests:        test result: ok. 23 positive suites, 15 compile-fail suites passed.

assets (SHA-256 in SHA256SUMS.txt):
  forge.exe  (… bytes)
  …
```

Attaching those assets to a release page is a **manual, optional** convenience for
whoever wants it; the pipeline neither needs nor performs it.

## Unchanged and still true

GitHub Actions remains blocked at the account level (*"The job was not started
because your account is locked due to a billing issue."*), which is now the second
reason the release path does not depend on it. `RELEASE_PROCESS.md` documents the
lock and states that a red/absent CI run means "not run", never "passed".
