# Morrow v2.3.3 — Resumable releases that don't lie

**Release date:** 2026-11-01
**Toolchain:** `forge 2.3.3 (morrow standalone 2026)`
**Self-hosting fixed point:** `8E46E0A47E4D8716FCF616702B7AD0FB9252CCEE64D92BDDEAC119F254E1FEF5`
(`target/stage2.exe.ll` == `target/stage3.exe.ll`)

v2.3.2 cut the GitHub CLI out of the release path. During that release, one more
defect in the same family showed up — not in publishing, in *reporting*.

## The bug

The pipeline is resumable (`--from build`, `--from package`, `--from publish`).
Build and test facts — the bootstrap parity hash and the suite summary — lived only
in the process that produced them. So a release resumed at `--from package` wrote
this into `dist/v2.3.2/PUBLISH.txt`:

```
fixed point:  n/a
tests:        n/a
```

Both gates had passed. The record said otherwise. A release manifest that answers
"n/a" for gates that ran is worse than no manifest: it makes a passing release
indistinguishable from one that skipped its checks.

## The fix

Stages now persist their facts to `target/pipeline-state.json`, keyed by tag, and
`package`/`publish` recover them when the earlier stage is not part of this run:

```json
{
  "tag": "v2.3.3",
  "version": "2.3.3",
  "parity": "8E46E0A47E4D8716FCF616702B7AD0FB9252CCEE64D92BDDEAC119F254E1FEF5",
  "suites": "test result: ok. 23 positive suites, 15 compile-fail suites passed.",
  "examples": 22
}
```

A resumed run logs what it recovered (`Recovered recorded facts: fixed point …, tests …`)
so the inherited numbers are visible rather than assumed. State from a *different*
tag is ignored — resuming a release never borrows another release's proof.

This release is itself the demonstration: it was cut as
`--no-publish` (build → test → bench → package → verify) and then resumed with
`--from package`, and its `PUBLISH.txt` carries the real hash and suite counts.

## Verification

| Gate | Result |
|---|---|
| 3-stage bootstrap | stage1/2/3 exit 0, `stage2.ll == stage3.ll` = `8E46E0A4…E254E1FEF5` |
| Native suites | 23/23 pass |
| Compile-fail suites | 15/15 reject with the documented diagnostic |
| Examples | 22/22 build |
| Benchmarks | all programs complete |
| Resumed publish | facts recovered from `target/pipeline-state.json`, not `n/a` |
| Publish mechanism | `git commit` + annotated tag + `git push` + `git ls-remote` verification; no host CLI |

## Still true

GitHub Actions remains blocked by the account billing lock documented in
`RELEASE_PROCESS.md` §6, which changes nothing for releases: they are made by git,
verified against the remote, and recorded in `dist/vX.Y.Z/` with checksums and a
manifest.
