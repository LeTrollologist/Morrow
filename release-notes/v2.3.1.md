# Morrow v2.3.1 — Release pipeline made release-safe

**Release date:** 2026-11-01
**Toolchain:** `forge 2.3.1 (morrow standalone 2026)`
**Self-hosting fixed point:** `AD5BABDB90BD740E95AE3C81F02513857E0E9048E468C86C022F17F6D1005E2B`
(`target/stage2.exe.ll` == `target/stage3.exe.ll`)

v2.3.0 shipped the default effect handlers *and* a local release pipeline
(`scripts/pipeline.py`). This release is the result of actually **playing that
pipeline in a sandbox**: the repo was cloned to a scratch directory, and the full
preflight → build → test → bench → package → verify sequence was executed there
before anything was published. Five holes surfaced. All five are fixed here, and
the pipeline now proves its own claims instead of asserting them.

## 1. A release could ship mislabelled (`version` stage)

The old pipeline never touched version declarations, so "releasing v2.3.1" would
publish binaries that still answer `forge 2.3.0` while `docs/SYNTAX.md` said
v2.3.0 too — the docs/version CI gate passed only because both were equally stale.

There is now a dedicated **stage 2 (`version`)** that rewrites every declaration
(`compiler/forge.mw`, `docs/SYNTAX.md` header and "verified against" line,
`README.md` badge, `Makefile` `TAG ?=`, `ROADMAP.md` status note), preserving line
endings, and then **fails if any declaration still disagrees** with the tag. Stage
3 (`build`) additionally asserts, after the three-stage bootstrap, that the
rebuilt binary reports the release version *and* that `docs/SYNTAX.md` agrees —
i.e. the release gate is enforced by the pipeline, not by memory.

## 2. Release notes were hardcoded

`stage_publish` used to write a fixed "Built-in Default Effect Handlers &
Concurrency" body for every tag. Notes now come from **`release-notes/vX.Y.Z.md`**
(tracked in git, shipped in the archive, used as the release body, and its first
heading becomes the release title). If the file is absent the pipeline emits a
factual skeleton — fixed point, suite summary, asset list — and says so; it never
invents feature claims.

## 3. The archive shipped build trees (38 MB → 7 MB)

Rehearsing the package stage produced a **38.77 MB** zip containing
`benchmarks/rust_tokio/target/release/deps/*.rlib`,
`compiler/target/crt/libstdc++.a` and `examples/target/crt/libgcc.a`. The packager
walked directories with `os.walk` and only filtered by file suffix, so nested
`target/` trees from earlier builds were swept in.

The walk now prunes `target/`, `dist/`, `__pycache__`, `node_modules`, `obj/` and
filtered intermediates (`.ll`, `.o`, `.obj`, `.pdb`, `.pyc`, `.rlib`, `.rmeta`,
`.lib`, `.exp`), and only ships `.exe` files from `bin/`. The `dist/` directory is
now git-ignored so packaging can never dirty the tree.

## 4. Publishing was not idempotent

`gh release create` was called unconditionally, and the tag check was local-only.
Publish now: creates the tag at `HEAD` (refusing to move an existing tag without
`--force`), pushes branch and tag, and then either **creates** the release or
**updates** it (`gh release edit` + `gh release upload --clobber`). It also
refuses to publish files it does not own unless `--force`, while auto-committing
the changes it does own (version declarations, `bin/*.exe`, `release-notes/`) as
`chore(release): vX.Y.Z`.

## 5. Test results were unchecked

`forge test` printed only `test result: ok. all test suites passed!`. It now prints
counts — `test result: ok. 23 positive suites, 15 compile-fail suites passed.` —
and the pipeline **fails if that line is missing or not ok**, writes the full log
to `target/pipeline-test.log`, and records the summary in the release notes.

## Documentation reconciled

- `RELEASE_PROCESS.md` rewritten for the real 8-stage pipeline
  (`preflight → version → build → test → bench → package → verify → publish`),
  including the publish semantics and the distribution layout.
- `docs/SYNTAX.md` §14 release gates corrected from "22/22 native suites, 13
  compile-fail suites" to **23/23 and 15** (the 23rd suite is v2.3.0's
  `default_effect_handler_test.mw`).
- `ROADMAP.md` CI description corrected to 23 positive suites.
- `Makefile` gained a `version` target and a correct `package` target.
