## The shared point, and why it is not one fix

The call-result type is produced in exactly one place per callee kind:

```
typeck.mw:737   let ret_sym = target_fn.ret_ty_sym;
typeck.mw:738   return tc_resolve_type(tc, types, struct_defs, ret_sym);
typeck.mw:745   let ret_sym = ext.ret_ty_sym;        (extern functions)
```

`tc_resolve_type` knows aliases and struct names only; `T` is neither, so it becomes
`ty_int`. Every generic-returning callee collapses there — **one** shared point, so no
`vec_get`/`hashmap_insert` special case is needed.

But the two false positives arrive with different information:

- **case 14** carries its instantiation in the **turbofish**, already stored in
  `expr.int_val`. A substitution at line 737 is sufficient, needs no new state, and is
  provably correct for that class.
- **case 16** has no turbofish. `T` is only knowable from the container's **element type**,
  which `TcType` does not record for struct instantiations (`Vec` stores `data`, `len`,
  `cap`, `arena` — not `T`). No lookup at line 737 can recover it. It needs element-type
  tracking, which is a representation change, not a rule.

A helper table of "functions that return their first argument's element" would make case 16
green while encoding the same kind of knowledge the project keeps deleting. Rejected on
purpose, and recorded as rejected.
