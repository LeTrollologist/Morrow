# Morrow v2.4.3 — The archive is reproducible too

**Release date:** 2026-11-01
**Toolchain:** `forge 2.4.3 (morrow standalone 2026)`
**Self-hosting fixed point:** `C48EA8C12A9CB4D5CE1F8496BAFFF62E5A6A2693A8B1469CC6080615F77858A0`
(`stage2.ll == stage3.ll` **and** `stage2.exe == stage3.exe`, 462848 bytes)

v2.4.2 fixed the compiler's own binaries. Re-running its pipeline to prove that
surfaced the same class of defect one level up: the *distribution archive* was still
not reproducible.

## What the verification run showed

An idle rerun of the v2.4.2 pipeline behaved exactly as it should — clean tree, tag
already at `HEAD`, `Everything up-to-date` on both pushes — and every individual
asset hashed identically:

```
forge.exe           A03F139F…   (both runs)
mwc.exe             A03F139F…   (both runs)
RELEASE_NOTES.md    0F1FF8AB…   (both runs)
Morrow-v2.4.2-win64.zip   2E7D8131…  vs  F05F50BD…   ← differs
```

The zip diverged because `zipfile` records each member's **working-tree mtime**, and
the build rewrites `bin/*.exe` on every run (same bytes, new timestamp). Identical
content, different archive bytes — so a released archive could never be verified by
rebuilding it.

## The fix

`stage_package` now writes every member through a `ZipInfo` with fixed metadata:
timestamp `1980-01-01 00:00:00`, `create_system = 0` (MS-DOS), mode `0644`. Content
is what varies; metadata does not.

Verified by packaging the same tree twice in a row:

```
Morrow-v2.4.2-win64.zip -> B83C18008B51558747ABB2F765F82B15C5A913740DE60760976E644DADF65E7F
Morrow-v2.4.2-win64.zip -> B83C18008B51558747ABB2F765F82B15C5A913740DE60760976E644DADF65E7F
```

## The reproducibility stack, as it now stands

| Layer | Gate | Status |
|---|---|---|
| Generated LLVM IR | `stage2.ll == stage3.ll` (build stage) | ✅ since v1.5.0 |
| Linked executable | `stage2.exe == stage3.exe` byte-for-byte (build stage) | ✅ new in v2.4.2 |
| Distribution archive | fixed zip member metadata (package stage) | ✅ new in v2.4.3 |

Any future regression in any layer fails the pipeline instead of silently producing
a "different but equivalent" release.

## Note on v2.4.2's local artifacts

While validating this fix, `dist/v2.4.2/` was re-packaged in place with the new
packager, so the zip on disk now hashes `B83C1800…` rather than the `2E7D8131…`
recorded at release time. The release itself is unchanged and unaffected: `v2.4.2`
is the tag `567d0f9`, and `release-notes/v2.4.2.md` is its record. `dist/` is build
output, not history.
