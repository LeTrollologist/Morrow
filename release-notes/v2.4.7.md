# Morrow v2.4.7 — Region escapes: the last store-shaped hole is closed

**Release date:** 2026-11-02
**Toolchain:** `forge 2.4.7 (morrow standalone 2026)`
**Self-hosting fixed point:** `BF4CE334D79DDA3CD46F4424943788E15F090782990C2EB373BBB77DD4EB5D15`
(`stage2.ll == stage3.ll`, `stage2.exe == stage3.exe`, 463872 bytes)

## The gap

v2.4.0 taught the checker to reject a region-scoped value written into a **struct
field**. The same leak through an **element store** was still invisible:

```morrow
region r {
    let p = morrow_region_alloc(r, 8, 8);
    slots[0] = p;        // compiled clean, dangled after the region closed
}
```

`stmt_index_assign` typed the base, the index and the right-hand side, then threw the
types away to pick an addressing mode.

## The fix

`stmt_index_assign` now applies exactly the rule `stmt_field_assign` already had: if
the value being stored is region-scoped and the holder is not, the program is rejected.

```
Region Escape Violation: region-scoped value stored in element of outer-scope value
```

The **holder is the root** of the index/field chain, so `a.b[i].c = x` is attributed to
`a` — a container that itself lives in the region remains a legal target.

Pinned by `tests/negative/region_index_store.mw`, which asserts the diagnostic text, so
a regression fails the suite. Compile-fail suites: **17 → 18**.

## Where escape analysis now stands

| Boundary | Status |
|---|---|
| `return` of a region-scoped value | rejected |
| Assignment to an outer-scope variable | rejected |
| Struct-field store into an outer-scope value | rejected (v2.4.0) |
| Element store into an outer-scope value | rejected (this release) |
| Indirect escape through a call (`take(&v)`) | **not detected** — needs interprocedural analysis |

One documented gap remains, and it is the one that genuinely requires cross-function
reasoning: a callee that stores or returns a borrowed region value. `docs/SYNTAX.md` §4
says so, and nothing else claims otherwise.
