# Morrow v2.4.2 — Windows binaries are reproducible again

**Release date:** 2026-11-01
**Toolchain:** `forge 2.4.2 (morrow standalone 2026)`
**Self-hosting fixed point:** `12038B761D4257FAD269A9F926AC59F7DA0BFC36D3D90A528ADA4C806A189469`
(`target/stage2.exe.ll` == `target/stage3.exe.ll` **and** `stage2.exe` == `stage3.exe` byte-for-byte)

Re-running the pipeline for an already-published release should have been a no-op.
It wasn't, and the failure was worth keeping.

## What the rerun exposed

The second build of v2.4.1 produced the **same IR hash** (`C19556C9…`, identical to
the first run) but **different `forge.exe` bytes** (`67091746…` vs `B16D9583…`,
same 462848-byte size). The build stage copies its output over `bin/`, so the tree
went dirty; the publish stage classified the change as pipeline-owned, committed it,
and then correctly refused to move the tag:

```
RuntimeError: Tag v2.4.1 points at 584166de but HEAD is 225775fe; pass --force to move it
```

Three real defects, one of them mine from the start:

1. **The linker stamped wall-clock time into the PE.** Reading the COFF header of the
   two binaries: `TimeDateStamp` `1793594462` (`04:41:02Z`) vs `1793596157`
   (`05:09:17Z`) — same size, same everything else.
2. **The fixed-point gate couldn't see it.** It compared `.ll` files, which were
   already reproducible; the *container* was not.
3. **Publish committed before validating**, so a rerun left a stray
   `chore(release): v2.4.1` commit behind for a release it then declined to publish.

## The fix

- `compiler/forge.mw`: the Windows link line now passes
  **`-Wl,--no-insert-timestamp`** (the C-baseline builder too), so the PE header
  carries a zero timestamp instead of the build clock.
- `scripts/pipeline.py` (`stage_build`): after the IR parity check, `stage2.exe` and
  `stage3.exe` must be **byte-identical** — they are linked from identical IR, so any
  difference means a non-deterministic linker. On failure the gate names the first
  differing offset. This release's own run reports:

  ```
  stage2.exe == stage3.exe byte-for-byte (462848 bytes).
  ```

- `scripts/pipeline.py` (`stage_publish`): the target tag is now validated **before**
  the tree is touched, so republishing a released version fails immediately with an
  explanation instead of committing regenerated binaries first.

## Evidence

Four back-to-back self-hosting builds from the same source:

| Binary | Linked by | SHA-256 |
|---|---|---|
| `s1.exe` | v2.4.1 (no flag) | `95BB869C…` |
| `s2.exe` | `s1` (flag) | `07CF2AC6…` |
| `s3.exe` | `s2` (flag) | `07CF2AC6…` |
| `s4.exe` | `s3` (flag) | `07CF2AC6…` |

Every compiler that carries the flag produces the same bytes, no matter when it runs.
(`s1` differs because it was linked by the previous release — which is exactly the
transition this release makes.)

The stray commit from the failed rerun was discarded (`git reset --hard 584166d`);
`main` never contained it.
