# Morrow v2.4.4 — Publishing is local, provable, and re-publishable

**Release date:** 2026-11-01
**Toolchain:** `forge 2.4.4 (morrow standalone 2026)`
**Self-hosting fixed point:** `855D0DD3C6339B915741343161467C23FA24361E5702335E3944DEC3DF114C40`
(`stage2.ll == stage3.ll`, `stage2.exe == stage3.exe` byte-for-byte)

This is the release that makes the pipeline answer for itself. Three things were
true after v2.4.3 and are fixed here: the release record lived nowhere in the repo,
re-publishing a version was an error rather than an operation, and the tag check
still assumed every publication puts the tag exactly at `HEAD`.

## 1. The repository now holds the release record

Every publication writes **`releases/vX.Y.Z.json`**, committed with the release:

```json
{
  "tag": "v2.4.4",
  "version": "2.4.4",
  "remote": "https://github.com/LeTrollologist/Morrow.git",
  "fixed_point": "855D0DD3…DF114C40",
  "tests": "test result: ok. 23 positive suites, 17 compile-fail suites passed.",
  "examples": 22,
  "notes": "release-notes/v2.4.4.md",
  "assets": [{ "name": "…", "bytes": 0, "sha256": "…" }],
  "published_at": "…Z",
  "republish_count": 0,
  "previous_publication": null
}
```

It records **no commit hash** on purpose: the record is committed alongside the
release, so any hash it stored would be invalidated by its own commit and every
rerun would look like a change. `git` answers "which commit is this tag"; the record
answers "which bytes were published, and did they verify". The archive carries
`releases/` too, so a distribution ships the record of what it is.

## 2. `--clobber` is a first-class operation

Re-publishing the same version is a legitimate need. It is now supported — and every
step of it refuses to be silent:

| Situation | Behaviour |
|---|---|
| `dist/vX.Y.Z/` already holds `PUBLISH.txt` | `package` refuses to overwrite; `--clobber` rebuilds |
| rebuilt artifact differs from the recorded publication | `verify` fails naming the asset; `--clobber` accepts and records the new bytes |
| version already recorded in `releases/` | `publish` refuses; `--clobber` records another publication |
| republication identical to the record | nothing is written, no commit is created — a clean no-op |
| `--clobber` when the tag is behind `HEAD` | allowed: the tag keeps identifying the release commit, the record lands on top |

`--clobber` never moves a tag; moving one stays `--force`. All four refusals were
exercised against v2.4.3 while building this release, with their real messages.

## 3. Two bugs the exercise found

- **The `--clobber` path could not finish.** The remote verification compared the
  peeled tag commit with `HEAD`, which is wrong by construction for a republication
  (the tag deliberately stays at the release commit). It now compares against the
  commit the tag actually identifies.
- **The record could churn forever.** Storing `commit` meant every publication
  invalidated its own record. Removed, and a republication that changes nothing now
  writes nothing.

## 4. Still no host, still no CI

Publishing is `git commit`, `git tag -a`, `git push`, `git ls-remote`. The preflight
guard still fails the run if `gh`/`glab`/`hub` ever appear in the release path, and
no Release object is created on any forge — GitHub shows the tag, and that is by
design. `RELEASE_PROCESS.md` §3 says so in plain words instead of implying otherwise.
