## 1. Executive summary

Morrow is a genuinely self-hosting, LLVM-backed programming language and toolchain
written in itself: 16 compiler modules (~13.3k lines of `.mw`), a ~2.9k-line standard
library, and ~3.2k lines of tests. The compiler emits LLVM IR and shells out to `clang`
to link. The repository is unusually candid in places (the §14 limitations table, the
release ledger, and the historical `AUDIT.md` are all good practice).

**The central engineering claim checks out.** I rebuilt the three-stage bootstrap from
the committed sources and reproduced the published fixed point exactly:

```
SHA256(stage2.exe.ll) = D9217D1E573A2837A2FEDCA46DCDCACD03F8E0255B835CA15218FA344D69F810
SHA256(stage3.exe.ll) = D9217D1E573A2837A2FEDCA46DCDCACD03F8E0255B835CA15218FA344D69F810
stage2.exe == stage3.exe byte-for-byte (471552 bytes)
```

`bin/mwc.exe` and `bin/forge.exe` are byte-identical to the hashes recorded in
`releases/v2.4.16.json`, and the entire 23 positive + 18 compile-fail suite passes.

**However, the language is not yet what its documentation describes.** The type
system is largely advisory, several core semantics are wrong or unimplemented, the
formatter destroys source files, effect handlers are silently bypassed for the
built-in effects, and 7 of the 21 shipped example binaries I executed fail at runtime.
The release gate compiles examples but never runs them, and one test suite cannot fail
by construction.

**Overall assessment:** an impressive research artifact and bootstrap demonstration,
but **not safe for production use** and not yet a sound systems language. The highest
priority is not new features — it is making the existing claims true and making the
release gate exercise the product the way a user does.

### Top risks

| # | Risk | Evidence |
|---|---|---|
| 1 | `forge fmt` silently corrupts source (drops imports/effects/`pub`, deletes comments, writes invalid or partial files) | Formatting `examples/collections_demo.mw` produced an unparseable file; formatting an invalid file rewrote it |

## 3. Architecture in one page

```
source .mw
  │
  ├─ lexer.mw      tokens (hand-written; comments/strings/ints)
  ├─ parser.mw     recursive-descent + precedence climbing → AST
  ├─ ast.mw        every node is a fixed 8-byte-field struct (region-allocated)
  ├─ forge.mw      module loader, handler desugaring, monomorphization
  ├─ typeck.mw     "bidirectional" checker + interval refinement solver
  ├─ tir.mw        basic-block SSA-ish IR; also performs built-in effect rewrites
  ├─ opt.mw        constant folding, dead code, bounds elimination
  ├─ codegen.mw    LLVM IR emitter + an embedded C runtime (region allocator,
  │                fs/process shims, effect frames, hand-written setjmp/longjmp)
  └─ clang        link (relative paths: lib/crt, system libs)
```

Supporting modules: `package.mw` (TOML/SemVer/lockfile), `forge.mw` (CLI),
`fmt.mw`, `json.mw`, `lsp.mw`, `smt.mw`, `diagnostics.mw`, `interner.mw`.

Self-hosting path: `bin/mwc.exe` is a stage-3 Morrow binary produced by
`stage2`, which was produced by `stage1`, which was produced by the shipped
`bin/mwc.exe`. The fixed point proves the compiler can reproduce itself from that
seed; it does not independently prove that the seed corresponds to the sources
(see M-04).

Notable representation choices that drive many findings:

- Every value is an `i64` in codegen. Structs are pointers to field arrays of
  `i64`; `Vec` slots are 8 bytes; `String` is a `char*`.
- Pointer/reference syntax is parsed but **discarded** (`parse_type` returns the
  pointee symbol), so `T`, `&T`, `&mut T`, `*mut T`, `*const T` are the same type
  to the checker.
- All integer widths except `u8`/`i8` map to `ty_int` (64-bit); `u8`/`i8` map to
  `ty_byte` for indexing/loads, but arithmetic is still 64-bit.

## 4. Findings

Severity: **C**ritical (data loss / core semantics broken), **H**igh (soundness,
security, or release-blocking), **M**edium (robustness/API/process), **L**ow.

### C-01 — `forge fmt` destroys source files

**Severity: Critical — silent data loss.**

`fmt_program` (`Morrow/compiler/fmt.mw:385-435`) only emits `extern "C"` blocks,
type aliases, structs, and functions. It does **not** emit:

- `import` declarations,
- `effect` declarations,
- `pub` visibility,
- `yields [...]` contracts,
- any comments (the AST has no comment nodes).

It also rewrites `->` to `:` and `let` to `var`, and `parse_type` has already thrown
away pointer/`&`/`*` syntax, so the formatter cannot reconstruct types correctly.
`format_file_source` writes the result back to the same path with no backup
(`Morrow/compiler/fmt.mw:437-480`), and it does this even when parsing reported
errors.

**Evidence.**

Formatting a copy of `examples/collections_demo.mw`:

```
$ forge fmt .tmp/fmt_imports.mw
Formatted file
$ head -6 .tmp/fmt_imports.mw
extern "C" {
    fn puts(s: u8): i32;        # was *const u8; imports are gone
    fn fflush(f: u8): i32;
}
$ forge check .tmp/fmt_imports.mw
[ERROR] Expected ';' after variable declaration (line 39, col 1)
...
```

Formatting a file that declares `pub struct`, `linear struct`, `affine struct`,
`effect E`, and a `yields [E]` function removed `pub`, removed the entire `effect E`
declaration, removed `yields [E]`, and deleted every comment.

Formatting `tests/invalid_syntax_sample.mw` (which does not parse) printed parser
errors and still wrote a fabricated `fn broken_function(: ) { ... }` over the
original.

**Impact:** a routine `forge fmt` on a real project can make it uncompilable and
delete declarations/comments. This is the single most dangerous behavior in the
repository.

**Fix:** do not ship `forge fmt` as-is. Make the formatter AST lossless (add comment
and declaration nodes, preserve pointer/ref syntax and `pub`/`yields`), refuse to
write when `diag_has_errors()`, and write to a temp file + rename only after the
output re-parses and re-typechecks. Add a golden test asserting semantic equivalence
and comment preservation, not just idempotency.

**Resolution (2026-11-08, data-loss guard).** `compiler/fmt.mw` now refuses to write
unless the candidate output tokenizes, parses, and its token stream matches the input
(ignoring only semicolons and trailing commas); comments, parse/lex errors, and any
construct the printer cannot represent are refused with a diagnostic and the file is
left byte-for-byte unchanged. `let`/`var` and `->` are preserved (via `AstStmt.is_mut`
and an explicit arrow), string literals are re-escaped, and replacement uses a
temp-file + backup + restore sequence instead of overwriting in place. Regression
tests were added to `tests/formatter_tests.mw`. Full lossless coverage (imports,
effects, `pub`, `yields`, pointers, comments) remains Phase 15 P0-1 in the roadmap;
the formatter currently refuses those files rather than corrupting them.

### C-02 — Effect handlers are bypassed for built-in effects in callees

**Severity: Critical — the headline language feature is unsound.**

`tir.mw:506-573` rewrites `perform` for four built-ins **unless the effect is
lexically handled in the same function** (`tir_is_effect_lexically_handled`):

| Effect/op | Rewritten to |
|---|---|
| `Process.spawn` | `process_exec` |
| `FS.read_file`, `read_file_in`, `write_file`, `file_exists`, `file_size`, `delete_file` | `fs_*` runtime shims |
| `IO.print` | `puts` |

The rewrite is **name-based and lexical**, not dynamic. A handler placed around a
call to a helper function therefore does not intercept effects performed *inside*
the helper; the real filesystem/process/console is used instead. It also ignores the
user's operation signature: a user-defined `effect IO { fn print(msg: i64) -> i64; }`
is compiled as `puts(inttoptr(msg))`.

**Evidence (FS handler in a callee is ignored):**

```morrow
effect FS { fn read_file(path: String) -> String; }
fn read_it() -> String yields [FS] {
    perform FS.read_file("definitely_missing_xyz.txt")
}
fn main() -> i64 {
    let r = handle { read_it() } with FS {
        fn read_file(k, path: String) { resume(k, "MOCKED"); }
    };
    unsafe { puts(r as *const u8); }   // prints "" (real missing file), not "MOCKED"
    0
}
```

Moving the `perform` lexically inside the `handle` block prints `MOCKED`, proving the
difference is the lexical rewrite, not the handler machinery.

**Evidence (shipped example):** `examples/generics_and_relational.mw` defines
`effect IO { fn print(msg: i64) -> i64; }`, performs it in `effectful_log`, and
handles it in `main`. The emitted IR for `effectful_log` is:

```llvm
%t103 = inttoptr i64 %t102 to ptr
%t104 = call i32 @puts(ptr %t103)
```

i.e. `puts((char*)42)`, which access-violates. The shipped binary exits
`0xC0000005` after printing 3 lines.

**Impact:** user handlers cannot mock or intercept `IO`, `FS`, or `Process` when the
effectful code lives in a function (the normal case). Tests that "mock" these effects
only work because their `perform` is lexically inside the `handle`. This is a direct
violation of the documented algebraic-effects model and is why several shipped
examples crash.

**Fix:** remove signature-blind, name-based rewriting from TIR. Implement default
handlers as real handler frames installed in `main` (or as explicit fallbacks at the
`perform` site only when no dynamic frame exists, with a signature match). Add tests
where the `perform` is in a callee under a handler for `IO`, `FS`, and `Process`.

**Resolution (2026-11-09, dynamic dispatch).** The TIR rewrite is gone: every
`perform` lowers to `tir_inst_effect_perform`. `codegen.mw` now returns static
default handler frames for `FS`, `Process`, and `IO` from
`morrow_effect_find_handler` only after the dynamic handler stack has been searched,
so a user handler around a callee always wins. Defaults are installed only for the
standard signatures: FS requires all six canonical operations, Process requires
`spawn(String, String)`, and IO `print` requires `String` (a user `IO.print(i64)` is
not turned into `puts((char*)int)`). Default dispatch functions perform the real
thunk call and resume the continuation. Regression tests were added to
`tests/effects_test.mw` for IO/FS/Process handlers around a callee; they crash/fail
on v2.4.16 and pass on the fixed compiler. Full suite: 23 positive + 18 compile-fail.

### C-03 — Pointer/reference semantics are erased; `&scalar` is the value, casts are no-ops

**Severity: Critical — `unsafe`/FFI code is miscompiled.**

Two code paths combine:

1. `parse_type` (`Morrow/compiler/parser.mw:83-104`) consumes `*`, `*mut`,
   `*const`, `&`, `&mut` and returns only the pointee/type symbol. A declared
   `*mut i64`, `&i64`, and `i64` are indistinguishable downstream.
2. Codegen for unary `&` returns the operand's **value**, not its address:

```morrow
// compiler/codegen.mw:673-674
if expr_ptr.op == tok_amp() {
    return inner_reg;
}
```

Codegen for a cast is a no-op:

```morrow
// compiler/codegen.mw:643-645
if expr_ptr.kind == expr_cast() {
    return emit_expr(cg, expr_ptr.left);
}
```

**Evidence.** This program compiles and access-violates:

```morrow
fn main() -> i64 {
    let mut counter: i64 = 42;
    let ptr: *mut i64 = &mut counter;
    unsafe { ptr[0] = 100; }
    unsafe { ptr[0] }
}
```

The generated IR is unambiguous:

```llvm
%t103 = add i64 0, 42
store i64 %t103, ptr %v_counter
%t104 = load i64, ptr %v_counter     ; value 42, not &counter
store i64 %t104, ptr %v_ptr
...
%t108 = inttoptr i64 %t105 to ptr   ; pointer = 42
%t109 = getelementptr inbounds i64, ptr %t108, i64 0
store i64 100, ptr %t109            ; write to address 42
```

`examples/ffi_demo.mw` is exactly this pattern and crashes with `0xC0000005`.

The bug is masked for structs/Strings/`Vec` because those values are already
pointers, which is why much of the compiler and stdlib appears to work.

**Impact:** address-of a scalar local, C out-parameters, `&mut` scalars, and any
pointer cast are broken. `as` between integer widths is also a no-op (see H-07),
because the cast node never reaches codegen.

**Fix:** either represent pointer/reference types in the AST/type system and lower
`&lvalue` to the `alloca` address, or explicitly reject `&scalar` and pointer casts
with a diagnostic. Do not silently emit the value.

**Resolution (2026-11-09, pointer semantics).** `parse_type` now retains `*mut`,
`*const`, `&`, and `&mut` in the interned type symbol; `tc_resolve_type` strips the
prefix for lookup and wraps the result in `ty_ptr`/`ty_ref`. Address-of a scalar
variable, field, or element lowers to its storage address; address-of a struct,
String, or existing pointer binding keeps the pointer value used by the
by-reference calling convention. Cast targets are type-directed: `u8/i8/u16/i16/
u32/i32` truncate and sign/zero-extend, while pointer/reference casts are i64
identity. `ffi_demo.mw` now exits 0, `&mut counter` writes 100, field stores through
`*mut Struct` use the correct offsets, and `u8` pointee indexing uses byte stride.
`&rvalue` is rejected with a diagnostic. Regression tests are in
`tests/syntax_features_test.mw`. Limitation: pointer spelling inside generic
arguments is normalized away (`Vec<*mut T>` identity is `Vec<T>`), and `&` on an
existing pointer binding still yields the binding value rather than a
pointer-to-pointer; both preserve the compiler's shallow-generic/by-reference model.

### H-01 — The type checker accepts undefined types and incompatible types

**Severity: High — soundness.**

`tc_resolve_type` falls back to `ty_int()` for any name it cannot resolve
(`Morrow/compiler/typeck.mw:429-430`), with no diagnostic. Return statements check
only refinement intervals, never the declared type kind
(`Morrow/compiler/typeck.mw:1524-1597`). Calls check existence and arity but compare
argument kinds only in report-only mode (`typeck.mw:686-710`, `752-812`).

**Evidence.** All of these pass `forge check` with "0 errors":

```morrow
fn takes_string(s: String) -> i64 { 1 }
fn main() -> i64 { takes_string(42) }          // wrong argument kind
```

```morrow
fn f() -> String { 123 }                        // wrong return kind
fn main() -> i64 { 0 }
```

```morrow
fn main() -> i64 {
    let x: NotATypeAtAll = 5;                  // undefined type
    x
}
```

`let` bindings do not verify that the initializer's kind matches the declared type:
the parser wraps the initializer in a cast to the annotation, and codegen drops casts,
so `let x: String = 5;` is accepted and stores the integer 5. Only refinement
intervals are actually checked (`typeck.mw:1304-1349`), and a missing return path is
accepted:

```morrow
fn maybe(c: bool) -> i64 { if c { return 1; } }  // passes; false path returns 0
```

**Impact:** typos and interface mismatches compile into wrong code (pointer/int
confusion, wrong return values) instead of diagnostics. Combined with C-03/H-07,
many programs are accepted that cannot be correct.

**Fix:** unknown type names must be errors (or explicit unsafe FFI types). Compare
kind/struct identity for arguments and returns; at minimum compare `ty_int` vs
`ty_string` vs `ty_struct`. Check all control-flow paths return a value. The
`tc_expr` inference gaps that caused the 152 false positives need fixing before
enforcement, but "no enforcement" is not an acceptable end state.

### H-02 — Region cleanup is skipped by `return`, `break`, and `continue`

**Severity: High — memory exhaustion; contradicts O(1) teardown.**

`region` entry allocates a 16 MB first chunk (`codegen.mw:4048-4050`). The normal
end-of-block path emits `morrow_region_exit`, but an explicit `return` inside the
block emits `ret` immediately (`codegen.mw:1531-1550`); `break`/`continue` jump to
the loop target. The `region_exit` block that follows is unreachable dead code.

**Evidence.** For a function that returns from inside a region, the IR is:

```llvm
%t109 = load i64, ptr %v_n
ret i64 %t109
bb_1:                                   ; unreachable
    %t110 = load i64, ptr %v_r
    %t111 = inttoptr i64 %t110 to ptr
    call void @morrow_region_exit(ptr %t111)
```

Twenty calls to such a function peaked at **336,879,616 private bytes** (~337 MB,
≈ 20 × 16 MB), versus ~4 MB working set; the regions were never returned.

**Impact:** `return` inside a region (a common early-exit idiom), `break`, and
`continue` leak the whole arena. The README's "O(1) teardown" claim is false on
these paths, and long-running loops can exhaust memory.

**Fix:** lower every early exit through a per-function cleanup path that calls
`morrow_region_exit` for each active region (or use a region stack + a single
epilogue). Add a runtime test that loops 10k times over a region with an early
return and asserts bounded RSS.

### H-03 — Unhandled effects and division by zero crash the process

**Severity: High — no runtime diagnostics; hard crashes.**

If a `perform` has no dynamic handler, `morrow_effect_find_handler` returns null
(`codegen.mw:4356-4367`) and the perform path immediately does
`getelementptr ... i64 16` and loads through it (`codegen.mw:3274-3379`), with no
null check. Minimal repro:

```morrow
effect E { fn op() -> i64; }
fn main() -> i64 yields [E] { perform E.op() }
```

compiles, then exits `0xC0000005` (access violation). The type checker validates
effect coverage for *calls*, but not for `main`'s own yields contract.

Integer division/modulo by a non-refined zero variable emits raw `sdiv`/`srem`
(`codegen.mw:714-733`); the refinement check only fires for refined divisors
(`typeck.mw:573-587`). `10 / z` with `z = 0` exits `0xC0000094`
(`STATUS_INTEGER_DIVIDE_BY_ZERO`).

**Impact:** ordinary mistakes become undebuggable process crashes. In a server
context this is a denial of service.

**Fix:** null-check the handler frame and report "unhandled effect \<name\>"; emit a
runtime divisor check (or define and enforce a trap with a readable message); make
`main`'s unhandled effects a compile error when no default is intended.

### H-04 — Shell command injection through output paths

**Severity: High — arbitrary command execution from a build invocation.**

`morrow_process_exec` concatenates `cmd` and `args` with a space and calls
`system()` (`codegen.mw:4243-4269`). `forge` builds the clang command by appending
`out_exe`/`out_ll` unquoted (`forge.mw:925-937`). Any shell metacharacter in `-o`
is interpreted. The same primitive is exposed to every Morrow program through
`std::process.process_exec`.

**Evidence.**

```
$ forge build .tmp/probe_ints.mw -o ".tmp/inj & echo INJECTED"
INJECTED .tmp\inj
INJECTED.ll lib/crt/crt2.o ...
forge: build succeeded
```

The shell ran the injected `echo`, and because `cmd.exe` returned the status of the
last command, the compiler reported **"build succeeded" even though clang failed**
with missing libraries.

**Impact:** a CI job or wrapper that lets a branch/project name influence the output
path can be made to execute arbitrary commands. Even without an attacker, paths with
spaces or `&` fail confusingly.

**Fix:** never use `system()`/`cmd.exe` for toolchain invocation. Use
`CreateProcessW` with an argv array (or `posix_spawn` on POSIX) and quote/escape
paths per platform. Propagate the child's real exit status, not the shell's last
command. Do the same for the `Process.spawn` runtime.

### H-05 — The release gate never runs examples; shipped artifacts are broken

**Severity: High — release quality / packaging.**

`pipeline.py:439-451` builds every example and counts successes, but never executes
one. The ledger records `"examples": 22` as if that were a runtime validation. Of
the 21 I ran, 7 failed (see §2.2), including 5 access violations and 2
missing-`sqlite3.dll` failures.

The SQLite packaging bug is concrete: `lib/crt/libsqlite3.a` is an **import
library** for `sqlite3.dll` (it contains the literal string `sqlite3.dll`), but the
repository contains no `sqlite3.dll`, and the package stage only copies repository
files. PE imports
of `sqlite_benchmark.exe` and `web_service.exe` are `KERNEL32.dll`, `msvcrt.dll`,
`sqlite3.dll`. Any program using `std::sqlite` fails to start unless the user
happens to have a compatible `sqlite3.dll` on `PATH`.

**Impact:** users download a release whose "portable" Win64 zip cannot run several of
its own examples. The README's SQLite/database story is unusable out of the box.

**Fix:** run every example with a timeout in the release gate and fail on abnormal
exit; run the network examples against a loopback socket or mark them `--run`-only.
Ship `sqlite3.dll` (with license) or statically link SQLite into the runtime. Add a
PE import check that every non-system DLL is present in the package.

### H-06 — Test-suite integrity: one suite cannot fail; failures are retried

**Severity: High — false assurance.**

- `tests/formal_verification_test.mw:15-22` defines `assert_true` to **print a
  message only**; it never changes the exit code, and `main` always returns 0. This
  is the suite that "verifies" mixed-sign intervals, zero-divisor proofs,
  path-sensitive narrowing, linear/affine resources, and the SMT bridge. It cannot
  detect a regression. A minimal copy of the pattern with `assert_true(1 == 2, ...)`
  prints the failure and exits 0.
- `forge_run_test` retries any non-zero test executable up to 10 times with
  `Sleep(200)` (`forge.mw:1151-1160`; same for benchmarks at `1323-1332`). A genuine
  assertion failure is re-run 10 times before being reported; a flaky test can pass
  on a retry. This masks timing/AV/file-lock failures.
- `tests/formatter_tests.mw:19-27` checks only idempotency. Garbage is idempotent;
  it does not check comment/declaration preservation, compilability, or semantics.
- `tests/crypto_test.mw` checks only determinism/distinctness, not known vectors;
  see M-06.
- The test list is hard-coded in `forge_run_test`; new `tests/*.mw` files are not
  discovered automatically.

**Impact:** the "23 + 18 passing" badge is true but weaker than it looks; the
formal-verification and formatter claims are effectively untested.

**Fix:** make `assert_true` call `exit(1)` (or return a status that `main` propagates);
remove the retry loop or restrict it to launch failures with a clear diagnostic;
add golden/negative tests for `fmt` (comments, effects, imports, `pub`, pointers);
add known-answer vectors for CRC/FNV/Adler; discover tests from disk.

### H-07 — Sized integer types are fictional; `as` does not convert

**Severity: High — miscompilation of normal arithmetic.**

`typeck.mw:288-304` maps `u64`, `u32`, `i32`, `u16` all to `ty_int` (64-bit) and
`u8`/`i8` to `ty_byte`. Codegen casts are no-ops (`codegen.mw:643-645`), i8 loads are
zero-extended (`codegen.mw:613-620`), and all locals are `alloca i64`.

**Evidence.**

```morrow
var a: u8 = 250; a = a + 10;      // 260, not 4
var b: i8 = 127; b = b + 1;       // 128, not -128
let y: u8 = 300 as u8;            // 300, not 44
let n: u8 = (0 - 1) as u8;        // -1, not 255
```

An `i8` array read of `-1` prints `255` (zero-extended, not sign-extended).
An integer literal larger than `i64` wraps silently: `999999999999999999999999999999`
compiles and evaluates to `1073741823` (the lexer accumulates with `i64` and no
overflow check, `lexer.mw:105-146`).

**Impact:** the type names `i8`/`i16`/`i32`/`u8`/`u16`/`u32`/`u64` give no width or
signedness guarantees; `as` is not a conversion. Programs that rely on integer width
(protocols, hashing, FFI, overflow checks) are silently wrong.

**Fix:** either implement width-aware arithmetic/casts (trunc/sext/zext, signed vs
unsigned compares/div) or remove the unsupported types from the documentation and
reject their use. At minimum, detect literal overflow and make `as` emit a real
conversion for pointer/int and width changes.

**Resolution (2026-11-09, sized integers).** `TcType` now carries `width`/`signed`;
the prelude gives `i8/i16/i32/i64/u8/u16/u32/u64` distinct metadata. Arithmetic
results are normalized with truncate+sign/zero-extend, assignments and field/index
stores normalize to the destination width, `i8`/`i16`/`i32` loads sign-extend,
`u8`/`u16`/`u32` loads zero-extend, and signed `sdiv/srem`/comparisons are used only
for signed operands (`udiv/urem` and unsigned comparisons otherwise, including
`u64`). Integer literals that exceed `i64` are diagnosed instead of wrapping.
`tests/syntax_features_test.mw` covers storage, arithmetic, field stores, array
loads, casts, and `u64`. Remaining limitation: struct fields still occupy 8-byte
slots (values are width-normalized, not packed), and `u64` values are carried in
the i64 register representation.

### H-08 — Documentation materially diverges from behavior

**Severity: High — users are misled about safety and semantics.**

Confirmed mismatches:

| Claim | Reality |
|---|---|
| `let` is an immutable binding (`docs/SYNTAX.md:418`) | `let x = 10; x = 99;` compiles and prints 99; `let`/`var` are the same AST node |
| `\0` is an accepted string escape (`docs/SYNTAX.md:46`) | Lexer handles only `\"`, `\n`, `\r`, `\t`, `\\`; `strlen("a\0b") == 4` (literal backslash + `0`) |

| "CSPRNG" (`README.md:206`) | `std/crypto.mw:139-181` is a deterministic LCG with the sign bit forced positive |
| "injection-safe SQL query builder" (`README.md:208`) | `std/sql_builder.mw:68-104` concatenates raw `table`, `columns`, `where`, `order` strings with no escaping |

`docs/GENERIC-TYPES.md` is also stale: it says `parse_type` erases `<...>` and "no
code was changed", while v2.4.16 interned concrete generic names (per its own

**Impact:** the "Verified Reality" section is itself not fully verified. Users will
trust `let`, `\0`, CSPRNG, and SQL-injection safety and be wrong.

**Fix:** make §14 and README match the code, add the README showcase to CI as a
compile test, and remove security adjectives ("CSPRNG", "injection-immune") unless
the implementation earns them.

### H-09 — The "standalone" compiler only works from the repository root

**Severity: High — the advertised `forge new` workflow is broken.**

The clang link line uses `lib/crt/crt2.o`, `-Llib/crt`, etc., all relative to the
current working directory (`forge.mw:925-932`); import resolution also looks for
`std/...` relative to the CWD (`forge.mw:66-106`). Running the compiler from any
other directory fails to link, and a scaffolded project cannot be built in place.

**Evidence.**

```
$ cd Morrow/.tmp && ../bin/forge.exe build probe_ints.mw -o probe_ints_cwd.exe
...
clang: error: no such file or directory: 'lib/crt/crt2.o'
forge: build failed with compilation errors
```

```
$ cd Morrow/.tmp && ../bin/forge.exe new demo
$ cd demo && ../../bin/forge.exe build src/main.mw -o app.exe
...
clang: error: no such file or directory: 'lib/crt/crt2.o'
```

Also, an unknown target triple silently falls back to the Windows branch (a
`--target bogus-triple` build produced an `MZ` executable and reported success),
and `forge_run_new` ignores `CreateDirectoryA`/`fs_write_string` failures and will
overwrite an existing `Forge.toml`/`src/main.mw`.

**Impact:** "standalone binary" and "scaffold a project" are false in practice; a
user must always `cd` into the distribution root, and typos in `--target` yield the
wrong artifact.

**Fix:** resolve runtime resources relative to the executable (or embed them), make
`forge new` produce a project that can find the toolchain, validate `--target`
against the supported set, and refuse to overwrite existing files without `--force`.

**Resolution (2026-11-09, standalone paths).** `forge.mw` locates its executable
with `GetModuleFileNameA` and resolves `std/`, `compiler/`, and `lib/crt` from the
installation root (with executable-directory and `src/` fallbacks), not the caller's
CWD. The Windows link suffix uses absolute `lib/crt` paths. `forge new` emits a
buildable `fn main() -> i64 { 0 }` project. Unsupported target triples now fail before
writing files or invoking clang. `tests/syntax_features_test.mw` builds a project
from `target/cwd_test`, scaffolds and builds a `forge new` project in place, and
checks that `--target bogus` fails. Remaining limitation: `forge new` still
overwrites existing `Forge.toml`/`src/main.mw` (tracked separately).

### M-01 — `&&` and `||` do not short-circuit

**Severity: Medium — surprising side effects and crashes.**

Both operands are emitted before the branchless `and`/`or`
(`codegen.mw:735-797`). `false && boom()` and `true || boom()` both execute `boom()`
and print. This also means a guard like `p != null && p[0] == 1` evaluates `p[0]`
on null.

**Fix:** lower to control flow (`br`/`phi`) and only evaluate the RHS on the needed
path; add tests with side-effecting RHS.

### M-02 — Parser robustness: stack overflow and silent truncation

**Severity: Medium — DoS on untrusted input.**

- Recursive descent has no depth limit. 20,000 nested parentheses or `if`s exits
  `0xC00000FD` (`STATUS_STACK_OVERFLOW`) in ~4 s; the LSP uses the same parser.
- An unterminated block comment is silently accepted (`lexer.mw:82-101`); everything
  after `/*` is dropped without a diagnostic. `fn main(){0} /*` compiles.
- `tokenize` uses `strlen`, so an embedded NUL byte truncates the rest of the source
  silently (`lexer.mw:44-46`), and several runtime shims use `strlen` on data that
  may contain NUL.
- Random-byte files exit cleanly (exit 1), but deep nesting crashes.

**Fix:** add a nesting-depth counter with a diagnostic; report unterminated
comments; track source length explicitly instead of `strlen`; run a small fuzz
corpus in CI.

### M-03 — LSP leaks memory and trusts `Content-Length`

**Severity: Medium — long-running editor DoS.**

`lsp_run_stdio` allocates the header buffer, body, and every response from one
arena that is never reset (`lsp.mw:427-490`). Each request permanently consumes
memory; a long editing session grows without bound. `content_len` is parsed as an
arbitrary decimal integer and passed to `morrow_region_alloc(arena, content_len+1)`
(`lsp.mw:466`); a huge value can overflow the `i64`→`usize` conversion or trigger a
giant allocation. The JSON parser is recursive with no depth limit. The server uses
Win32 `GetStdHandle`/`ReadFile` only and has no POSIX path. `tests/lsp_test.mw` calls
`lsp_handle_request` directly and never exercises the stdio loop.

A basic end-to-end session (initialize → didOpen → shutdown → exit) does work and
produced valid framed JSON in my test.

**Fix:** use a per-request arena/region reset (or a ring of regions), cap
`Content-Length` (e.g. 8 MB) and reject overflow, add JSON depth limits, and add an
end-to-end stdio test plus a memory-growth test.

### M-04 — Release pipeline hazards

**Severity: Medium — process/integrity, not code execution.**

1. **`make build`/`test`/`bench`/`package`/`verify` can publish.** The targets pass
   `--skip publish` but not `--skip ship`; `ship` is a later stage and still runs
   because `--skip publish` does not set `no_publish`. My `--from build --skip …
   --skip publish` run completed the fixed point, then invoked
   `release_page.py`, failed with "no GitHub token", and exited 1. Depending on the
   token/environment, `make test` can create/update a GitHub release page.
2. **Tags are always force-pushed.** `pipeline.py:838` runs
   `git push origin <tag> --force` unconditionally. The pre-check only looks at
   local refs (`pipeline.py:749-766`); on a fresh clone that lacks the remote tag,
   it will create and force-overwrite an existing release tag, contrary to
   `RELEASE_PROCESS.md` ("moving an existing tag requires `--force`").
3. **Stale binaries can be packaged.** `--from package`/`--skip build` does not
   verify that `bin/*.exe` was built from the current sources; preflight only warns
   if the version string differs.
4. **No independent bootstrap.** The three-stage loop trusts the shipped
   `bin/mwc.exe` as stage 0. A compromised seed can produce a self-consistent
   compiler; the fixed point proves self-reproduction, not correspondence to source.
   There is no signed ledger, no independent seed, and no CI.
5. **Benchmarks are unfair.** Morrow output is linked without `-O2` (the clang line
   in `forge.mw:926` has no optimization flag), while C baselines are compiled with
   `-O2` (`forge.mw:1364`). The reported 1M vs 33M req/s gap is partly an
   optimization-level artifact.
6. `pipeline.py` uses `shell=True` with the tag interpolated into commands
   (`run()` at lines 68-73; tag validation is absent). A tag containing shell
   metacharacters is operator-controlled but still a foot-gun.

**Fix:** make `--skip publish` imply `--skip ship` (or gate `ship` behind an explicit
`--ship`), never force-push a tag without `--force`, validate tag format
`^v\d+\.\d+\.\d+$`, verify `bin` hashes after build, compile Morrow benchmarks with
`-O2`, and document the seed-trust limitation.

### M-05 — Standard-library API hazards

**Severity: Medium — memory unsafety behind safe-looking APIs.**

- `vec_pop` on an empty `Vec` sets `len = -1` and reads `data[-1]`
  (`std/collections.mw:117-123`); `vec_get` performs no bounds check
  (`collections.mw:125-129`). `vec_pop(&mut vec_new())` returned garbage and a
  subsequent `vec_get(v, 1000000)` exited `0xC0000005`. These APIs are not marked
  `unsafe` and are presented as a safe collection.
- `hashmap_get` returns `-1` both for "missing" and for a stored value of `-1`
  (`collections.mw:487-517`), so a legitimate `-1` is indistinguishable from
  absence; `hashmap_contains` is required but not enforced.
- `command_arg` assigns `cmd.args = arg` instead of appending (`std/process.mw:16-18`),
  so only the last argument survives. Arguments are also unquoted (H-04).
- `string_buffer_push_str` requires 3 arguments but its body still contains a
  "2-argument fallback" comment and a `text_len <= 0` branch
  (`collections.mw:219-233`). Under arity enforcement the 2-arg form cannot compile;
  the fallback is dead and the README uses the dead form (H-08).
- `morrow_alloc(size, align)` ignores `align` (`codegen.mw:4042-4046`); region
  chunks are 16-aligned regardless of the requested `align` (`codegen.mw:4090-4105`).

**Fix:** bounds-check `Vec` (or mark it `unsafe`); use an explicit `Option`-like
result for map lookup; append arguments; delete the dead fallback; honor alignment
or document the 16-byte limit.

### M-06 — Hashes and "CSPRNG" are not what they are called

**Severity: Medium — security/integrity misrepresentation.**

`std/crypto.mw` implements:

- `crc32_hash`: `crc = crc + b * 2654435761` mod 2^32, with sign fixups — this is
  **not CRC-32** (no polynomial, no table, no reflection). `crc32("123456789")`
  returns `3445472972`; the standard CRC-32 is `3421780262`.
- `fnv1a_hash`: uses a wrong offset basis (`1469598103934665603` vs
  `14695981039346656037`), uses `(h + b) * prime` instead of `(h ^ b) * prime`, and
  forces the result positive. `fnv1a("hello")` returns `7081551233511078179`; the
  standard 64-bit FNV-1a is `11831194018420276491` (`-6615550055289275125` signed).
- `adler32_hash` does match the standard (`300286872` for "Wikipedia").
- `CryptoRng` is a seeded LCG (`seed * 6364136223846793005 + …`) with the sign bit
  forced positive. It is deterministic and unsuitable for cryptographic use, despite
  the name and the README's "CSPRNG".

The tests only assert determinism and "two inputs differ"; they do not use known
vectors.

**Fix:** either implement the standard algorithms (with test vectors) and a real OS
CSPRNG (`BCryptGenRandom`/`getrandom`), or rename them (`fast_hash`, `lcg`) and
remove the CSPRNG claim. Do not ship security-sensitive names for non-standard code.

### M-08 — ABI and runtime fragility

**Severity: Medium — latent miscompilation, currently masked by `-O0`.**

- Every `extern "C"` declaration is emitted as `i64 @name(i64, …)`
  (`codegen.mw:3950-3961`). Only a hard-coded list of libc/Win32 names gets
  truncation/sign-extension (`strcmp`, `strlen`, `Sleep`, `CreateProcess`-adjacent
  wrappers, etc.). Arbitrary C functions returning `i32`, taking `short`/`char`, or
  passing structs by value are ABI-wrong. Negative `i32` returns can appear as large
  positive `i64` values.
- `morrow_setjmp`/`morrow_longjmp` are hand-written assembly declared as ordinary
  functions; LLVM is not told `returns_twice`. At `-O0` the tests pass, but at
  `-O1+` LLVM may cache values across the `setjmp` call in registers that `longjmp`
  does not restore. This is a latent miscompile if optimization is ever enabled.
- On `wasm32`, `morrow_setjmp` returns 0 and `morrow_longjmp` is a no-op
  (`codegen.mw:3708-3716`); a handler/resume on wasm silently returns 0 instead of
  resuming. The docs only verify wasm magic bytes, not behavior.
- Hard-coded field-offset (`get_field_offset`, `codegen.mw:191-283`) and byte-stride
  (`is_byte_indexing`, `codegen.mw:285-314`) tables keyed on identifier names remain
  as fallbacks. They are only reached when the checker leaves `op == 0` (unknown
  types/FFI), but that is exactly the case where silent wrong layout is possible.
  This contradicts `AUDIT.md`'s claim that F-07 was fully fixed.
- `main` is always emitted as `i32 @main()`; parameters on `fn main(...)` are
  ignored/spilled from non-existent SSA values.

**Fix:** model C signatures (or at least `i32`/pointer/struct) in `extern`
declarations; mark setjmp `returns_twice` (or use a real coroutine/stack-switch
design); implement wasm effects or reject handlers on wasm; remove name-keyed layout
fallbacks by making the checker always annotate offsets/stride.

### M-09 — `println` of a dynamic string prints a pointer

**Severity: Medium — silent wrong output / info leak.**

The codegen special-cases `println` only when the first argument is a **string
literal** (`codegen.mw:2505-2589`). A `String` variable, a function returning a
string, or a `{}` placeholder whose value is a non-literal string is emitted as
`printf("%lld", value)`, i.e. the pointer address.

**Evidence.**

```morrow
let t = "hello";
println(t);                 // prints 140698758627413
println("{}", diag_primary_message());  // prints the pointer, not the message
```

**Fix:** use the static type to choose `%s` for `String` expressions (the checker
already knows `ty_string`), or provide a distinct `print_string` intrinsic. Do not
silently print addresses.

## 8. Bottom line

The bootstrap and test numbers are real. But the product currently fails the
"systems language" bar on the properties users will rely on: sound typing,
predictable integer/pointer semantics, memory cleanup, dynamic effect handlers,
and a formatter that does not destroy code. The repository's own §14 is honest
about many limitations; the problem is that several claims outside §14 — immutable
`let`, `\0`, CSPRNG, injection-safe SQL, "standalone", "examples work" — are not
true, and the release gate does not exercise the runtime.

If the project wants to be taken seriously as a language, the next release should
be a **correctness release**, not a feature release: disable destructive tooling,
fix effect dispatch and pointer semantics, enforce a minimal type discipline, run
examples in CI, and make the documentation match `forge check` output.
